在 Nail 里做业务 Agent 时，一个反复出现的问题是，用户问得很自然，数据却需要经过很多层解释才能回答。

“这个区域还有哪些值得拓展的门店？”这样一句话，涉及区域范围、门店分类、品牌客户、匹配关系、销售表现和潜力规则。最终还可能需要一份名单、一张地图和一个可下载的表格。

模型需要理解这些概念，查询程序需要准确执行，图表与导出还要延续同一套含义。我因此开始尝试本体，希望把业务对象及其关系明确地表达出来，让 Agent 有一份可以引用、可以检查的业务定义。

这篇文章依据 Nail 留存的本体实验、技术合同、查询验证和后续主线调整记录，整理这段探索中形成的认识。文中的门店数量和覆盖率示例均为便于说明而构造。

## 本体在这个项目里解决什么问题

本体用形式化方式表达一个领域中的概念及其关系。以门店业务为例，需要定义门店、经销商、商品、交易等对象，说明它们怎样关联，以及某些分类和关系可以推出什么结论。OWL 2 提供了类、属性、个体等表达能力。[W3C OWL 2 概览](https://www.w3.org/TR/owl2-overview/)

落到 Nail，我最关心的是几个很具体的问题。

- 用户说的“客户”和地图上的“门店”，分别指哪一种对象？
- 两套来源里的门店记录，凭什么关联？
- 某个指标采用什么粒度、单位、期间和公式？
- “未覆盖”这个结论需要哪些完整数据和关系证据？
- 回答里的数字、地图上的点和导出的名单，怎样对应到同一次计算？

这些问题横跨语义定义、来源映射、业务计算和结果交付。本体提供其中的概念与关系表达，整个业务系统还需要查询、权限、精确计算和持久化共同工作。

## 第一个难点是确定对象的身份

做门店分析时，几种对象在界面上都可能被叫作“门店”。

| 对象 | 在业务里代表什么 | 关联时需要核对什么 |
| --- | --- | --- |
| 地图 POI | 某个地图来源中的地点记录 | 来源、原生编号与版本 |
| 经销商的客户记录 | 某个经销商业务范围内的客户 | 来源及完整客户身份 |
| 品牌客户名单中的门店 | 某次发布名单里的记录 | 名单版本与记录身份 |
| 匹配关系 | 两种记录之间经过判定的联系 | 关联依据、状态和适用版本 |

同一个实体门店可能对应多条业务记录。一条客户记录也可能保留多个匹配候选。

如果在这个阶段丢失来源，把名称当成唯一标识，后面的指标计算就会受到影响。一笔销售经过一对多关联展开，金额可能被重复累加。多个经销商确实向同一家店供货时，又需要保留各自真实的交易。

Nail 的实践逐渐把身份、匹配、分配和同一性分别建模。标准本体合同要求保留完整原键，对前导零、空值和来源上下文作明确处理。名称相似度、距离和区域分配则各自保存含义与依据。

回头看，整理身份定义是很有价值的一步。它会迫使我把“这两张表能连起来”进一步说明成“为什么能连、会不会展开、关联失败怎样处理”。

## 我们走过的几种实现

Nail 的本体探索经历了自定义资源与查询原型、标准组件验证，以及后来的 PostgreSQL 标准本体路线。

早期的自定义 JSON 资源和执行器，把实体、关系、指标和查询约束显式组织起来。这个阶段帮助梳理了业务模型，同时也带来了需要自行维护的语义解释与查询执行逻辑。

随后进行了标准组件选型和隔离小样验证。留存记录中，有一轮使用 Ontop、Jena 和私有 MySQL 实例的实验。后续标准路线转向 PostgreSQL／PostGIS，形成 RDF／OWL、R2RML、SHACL 与 Node 运行时之间的技术合同。

这些组件的分工大致如下。

| 组件或标准 | 在这条路线中的职责 |
| --- | --- |
| RDF／OWL | 表达业务对象、属性、分类与关系 |
| R2RML | 将关系数据库中的数据映射为 RDF |
| Ontop | 将虚拟图上的 SPARQL 查询转换为来源库 SQL |
| Jena／SHACL | 离线解析资源并检查样本图约束 |
| PostgreSQL／PostGIS | 执行关系数据查询与相应空间计算 |
| Node 运行时 | 校验计划、权限和来源，组合结果并完成发布 |

RDF 使用三元组表达事实，R2RML 描述关系数据到 RDF 的映射。Ontop 采用虚拟知识图谱方式，数据可以继续保留在原关系库中，通过映射接受图查询。[RDF 数据模型](https://www.w3.org/TR/rdf11-concepts/)、[R2RML 规范](https://www.w3.org/TR/r2rml/)、[Ontop 官方介绍](https://ontop-vkg.org/guide/)

标准组件也带来了需要核实的能力范围。项目合同只开放经过登记和验证的有限分类、逆关系与关系路径，并记录了具体数据类型的兼容限制。每一种声明都需要对应到实际执行行为。

留存的小样里，一轮 MySQL 实验修正适配问题后记录了 24 项通过、7 项未运行，方案 B 尚未执行。后续 PG 路线有资源、运行时实现和隔离检查，生产来源保护、部署配置及完整验收仍有待完成。这些记录支持讨论局部能力和失败原因，方案间的完整成本比较还需要更多证据。

归档中的那轮真实模型复验，完整短题和复杂调查均未取得成功终态，商品组合查询仍出现执行超时。资源和局部查询检查通过后，完整回答、界面展示、保存与导出仍需逐项验收。

## 指标定义需要比名称更具体

“销售额”“覆盖率”“有销门店”看起来都是常见词，真正执行时却需要很多前提。

以覆盖率为例，假设一个获准分析的市场范围里有 100 家符合条件的门店，其中 20 家有经过确认的品牌关联。按这一定义，覆盖率是 20%。

如果查询先沿品牌关联筛选，得到 20 家，再把这个集合同时用于分子和分母，就会得到 100%。查询语句可能顺利执行，统计含义却已经改变。

Nail 的本体合同因此把完整市场范围、关系筛选和指标分母作了明确约定。指标需要携带事实集、粒度、单位、期间、允许维度、缺失值处理和版本化的执行绑定。

“有销”也需要单独定义。某家店发生销售和退货，净额可能为零或负数，交易活动仍然发生过。只看净额正负，就可能把活动判断错。

缺失值同样会影响结论。确认取齐了规定范围的对象，并且指标定义允许时，缺少事实才可能解释为结构性零值。未匹配、未知和没有取到数据，都需要保留各自状态。

这类工作让本体探索与指标治理联系起来。一项指标的名字只是入口，真正让它可复用的是完整定义，以及定义对应的确定性执行。

## 关系和推理要能改变结果

描述业务关系时，很容易画出一张丰富的概念图。进入实现后，我会进一步追问，每一条关系究竟影响了什么查询。

例如，声明某个退货类型是一个更一般交易类型的子类，应当影响相应的类型查询。登记了逆关系，应当能沿明确的方向找回对应对象。关系路径还需要约定起点、终点、方向及允许经过的步骤。

Nail 的标准合同要求，相关公理的删改应改变查询结果，或者触发校验拒绝。这为“语义有没有真正参与执行”提供了可检查的标准。

业务判断则需要额外前提。“未覆盖”依赖完整范围和可信关联，“高潜”依赖明确规则及输入，“有销”依赖规定期间内的实际交易事实。每一项结论都需要说明输入是否完整、规则如何执行、适用于什么范围。

SHACL 可以检查给定 RDF 图是否符合 shapes 中描述的条件。项目还需要通过来源核验、SQL 对账和业务规则测试，检查事实完整性与计算含义。[W3C SHACL 规范](https://www.w3.org/TR/shacl/)

## 一次分析需要交付同一份结果

业务 Agent 的输出可能同时包含文字、表格、图表、地图和文件。它们之间的一致性，也是这次本体实践里投入很多工作的部分。

假设回答说找到 20 家门店，地图按另一套筛选显示了 18 个点，导出又在数据刷新后查到了 21 行，用户就很难核对这次分析。

Nail 在本体结果与后续历史兼容实现中，逐步建立了固定结果、来源版本、精确值和交付回执。不同展示引用已经保存的结果，再按各自方式呈现。

```text
获准来源与业务定义
        ↓
查询、计算与来源核验
        ↓
保存结果及其版本依据
        ↓
文字 / 表格 / 图表 / 地图 / 导出
```

这里的地图还需要说明可绘制范围。一份名单中的记录可能缺少有效坐标，名单数量和地图点数因此需要分别解释，同时保留两者的对应关系。

版本也需要贯穿保存与恢复。用户重新打开一份历史分析时，需要知道它采用了当时哪一版数据、映射和规则。后续更新定义时，历史结果仍然有自己的解释依据。

## 校验程序也会制造新的失败

本体实验让我开始更具体地看待一次失败发生在哪个环节。

### 十进制零值的格式

一轮隔离小样中，Ontop 返回的十进制零值采用了 `0E-12` 这样的词法形式，Nail 的结果合同要求普通十进制文本，因此发生了兼容问题。

后续适配通过精确词法规范化，将这个值转换成 `0`，避免经过浮点数和舍入。这解决了组合适配中的问题，也保留了原始词法检查失败的记录。

这个例子提醒我，业务值、传输类型和文本表示都需要检查。一个值经过数据库、JDBC、查询端点和应用层，每一层都可能引入新的表达差异。

### “这一项”被当成业务数量

另一次真实短题记录中，正文里的普通说明“这一项”被校验器识别成需要绑定证据的业务数量，导致回答被拒绝。

同一份排查记录里，还出现过查询净额正确、交付核对却误报筛选不一致的情况。后续离线修复回放可以核对这个局部程序问题，完整用户任务仍需重新验收。

这让我开始检查校验器自身的输入、判断条件和错误提示。过度拦截会影响正常交付，漏检则会放过真实错误，两种情况都需要具体样本。

### 相同错误码可能来自不同阶段

已有记录中，一次查询确实返回了执行超时。调查停止后再次发起请求，停止守卫也返回了超时状态。

定位时需要继续看请求是否进入执行器、SQL 是否实际开始，以及失败来自哪个阶段。记录里缺少原 SQL 和阶段证据时，具体性能原因仍需调查。

我从这些例子里学到的排查方法，是保留原问题、实际参数、工具返回和最终产物，找到最早出现偏差的位置，再验证一个具体原因。

## 后来，主线做了精简

2026 年 11 月 2 日，Nail 合入精简主线，继续采用 Pi、Skill、只读 SQL 和地图工具。本体版本保留在 `ontology-agent` 分支。后续主线移除了退役的本体执行器，同时保留历史结果、图表、地图和导出的读取兼容。

从这段实践里，我看到了完整语义运行系统的维护范围。除了概念定义，还包括来源映射、资源发布、查询改写、精度处理、执行预算、取消恢复、结果保存和展示校验。任何一层变化，都需要重新确认受影响的行为。

主线调整记录说明了实现路线的变化。关于成本与效果，我更愿意保留实验记录本身的范围，继续积累相同问题、相同数据和相同交付要求下的比较。

对我而言，这段探索已经留下了可以继续使用的工作成果。门店身份的边界更清楚了，指标开始带着完整口径，结果需要可追溯，失败也需要按实际阶段定位。这些要求会继续影响后面的 Agent 开发。

## 再做一次，我会从一个可对账的问题开始

如果重新开始，我会先选一个范围明确的问题，例如查询某个获准区域、某个期间的门店销售，并交付完整名单。

先整理对象身份与关联依据，再选一份业务认可的报表或 SQL 作对账基准。随后写清期间、单位、退货、缺失值和去重规则，让一次查询能够稳定复现。

在这个基础上，再判断哪些分类、关系和规则值得形式化，哪些查询需要借助标准语义组件，并检查它们是否真正改变了结果、减少了重复实现。

这次做本体，给我留下最深的体会是，业务 Agent 要可靠地回答一个问题，需要有人把概念、数据和计算之间的约定逐项说清楚。模型可以参与理解和组织任务，系统则需要保存这些约定，并让最终交付可以核对。
