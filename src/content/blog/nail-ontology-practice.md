当我们让 Agent 分析业务数据时，经常会遇到这样的问题。用户说“看看这个区域还有哪些值得拓展的门店”，系统却需要先弄清楚，区域怎样划定、门店指哪类对象、已经覆盖怎样判断、值得拓展采用什么规则。

这些词背后的含义，会影响模型选择工具、程序查询数据，以及最后生成的名单和图表。本体论提供了一套显式描述概念和关系的方法，让这些业务含义可以被共享、引用和检查。

我在 Nail 的业务 Agent 中尝试过这套方法。结合那段实践，本文从基本概念开始，介绍本体如何表达业务，以及如何接入一个实际的 Agent 项目。

## 什么是本体论

Ontology 常被译为“本体论”或“本体”。在知识工程中，本体是对一个领域中概念及其关系的显式、形式化描述。

“显式”意味着把定义写下来。例如，“便利店属于门店”“订单由客户提交”，需要成为明确的声明。

“形式化”意味着使用有确定语义的表达方式，让程序能够读取、检查，并在相应规则和引擎支持下推导事实。OWL 2 是表达这类本体的标准语言之一，提供类、属性、个体和数据值等构造。[W3C OWL 2 概览](https://www.w3.org/TR/owl2-overview/)

以门店经营为例，可以先认识五种基本元素。

| 元素 | 表达什么 | 示例 |
| --- | --- | --- |
| 类或概念 | 一类事物 | 门店、便利店、经销商、商品 |
| 个体或实例 | 一个具体对象 | 某一家门店、某一个经销商 |
| 数据属性 | 对象的具体取值 | 名称、地址、营业面积 |
| 对象关系 | 对象之间的联系 | 经销商向门店供货、订单包含商品 |
| 公理 | 分类与关系所遵循的形式化声明 | 便利店是门店的子类 |

把这些定义组织起来，系统就能理解“门店”涵盖什么、对象之间可以怎样关联，以及某些结论来自什么声明。

例如，已知便利店是门店的子类，某家店是一家便利店，在支持相应 RDFS 推理的系统中，就可以推出它也是一家门店。[W3C RDF Schema](https://www.w3.org/TR/rdf-schema/)

## 本体在业务系统里处于什么位置

一个业务系统通常已经有数据库、接口、文档和各种规则。本体为这些部分提供共享的概念与关系定义。

| 系统中的部分 | 主要承载的内容 |
| --- | --- |
| 数据库 Schema | 表、字段、键与数据结构 |
| 本体 | 领域概念、属性、关系与公理 |
| 知识图谱 | 具体实体及其相互关联的事实 |
| 指标定义 | 计算粒度、公式、单位、期间和缺失值处理 |
| 业务服务 | 授权、状态变化、交易和实际动作 |
| 检索知识库 | 可检索的文档、说明与参考资料 |

这些部分可以相互引用。例如，本体定义“门店”和“经销商”，数据库保存具体记录，映射说明数据库记录如何对应业务对象，指标定义规定怎样计算门店覆盖率，业务服务执行查询和授权。

在 Agent 项目中，Skill 可以指导某类任务怎样完成，检索工具可以找到业务说明，本体则让这些说明里的对象和关系有稳定含义。工具接口把这些定义连接到实际操作。

工程上也需要区分逻辑推导与业务判断。“便利店属于门店”可以用类层级表达，“高潜门店”则通常需要评分公式、输入数据和适用条件。后者可以登记在语义资源中，并绑定到确定的计算程序。

## 为什么 Agent 项目会用到本体

业务人员通常用领域语言提问，数据系统使用表名、字段和接口参数。Agent 需要把两者对应起来。

以“查找某区域尚未覆盖的便利店”为例，至少需要明确三件事。

第一，**词语对应什么概念**。“便利店”是否包含某些细分类别？“客户”指经销商客户，还是品牌名单中的客户？同一个词在不同业务上下文中可能对应不同对象。

第二，**对象怎样关联**。品牌客户记录如何关联地图 POI？关联依据是什么？一个对象对应多个候选时怎样处理？

第三，**结论需要什么前提**。“未覆盖”需要明确市场范围、覆盖定义和完整的关联数据。来源中缺少一条关联时，需要结合数据完整性判断其含义。

本体可以把概念、关系及相关定义组织成可查询的目录。Agent 先发现可用概念和能力，再选择工具执行。服务端根据相同定义检查参数、关系路径和执行条件。

在 Nail 中，门店身份就是一个很实际的例子。地图 POI、经销商客户记录和品牌名单记录，各自具有来源与身份。明确这些对象后，查询才能进一步讨论匹配、去重和覆盖。

## RDF、OWL、SHACL 和 SPARQL 分别做什么

第一次接触本体时，容易同时遇到一批缩写。可以按照“表达事实、定义含义、检查数据、查询数据”的顺序理解。

| 技术 | 作用 | 一个直观例子 |
| --- | --- | --- |
| RDF | 用三元组表达事实 | 门店 A — 位于 — 区域 B |
| Turtle | 将 RDF 写成文本的一种语法 | 把三元组保存到 `.ttl` 文件 |
| RDFS | 表达类层级和属性等基础语义 | 便利店是门店的子类 |
| OWL | 表达更丰富的形式化语义 | 等价类、互斥类、逆关系 |
| SHACL | 检查 RDF 图是否满足规定条件 | 门店名称必须存在且为字符串 |
| SPARQL | 查询 RDF 数据 | 找到属于某区域的全部门店 |
| R2RML | 描述关系数据库到 RDF 的映射 | 将客户表中的记录映射成业务对象 |

RDF 的基本单位是主语、谓语、宾语组成的三元组。SPARQL 可以在 RDF 图上匹配模式，执行筛选和聚合。查询对隐含事实的可见性，取决于系统采用的推理或查询改写配置。[RDF 数据模型](https://www.w3.org/TR/rdf11-concepts/)、[SPARQL 查询语言](https://www.w3.org/TR/sparql11-query/)

### 一个最小的本体示例

下面用 Turtle 声明两个类，并记录一家示例便利店。

```turtle
@prefix ex: <https://example.org/business/> .
@prefix owl: <http://www.w3.org/2002/07/owl#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

ex:Store a owl:Class .

ex:ConvenienceStore a owl:Class ;
    rdfs:subClassOf ex:Store .

ex:name a owl:DatatypeProperty .

ex:store001 a ex:ConvenienceStore ;
    ex:name "示例便利店" .
```

这里的 `ex:` 是命名空间前缀。`a` 表示类型关系，`rdfs:subClassOf` 表示子类关系。`ex:store001` 是一个具体实例的标识，名称是它的属性值。

在启用了相应子类推理或查询改写的环境中，查询 `ex:Store` 可以包含这个便利店实例。

```sparql
PREFIX ex: <https://example.org/business/>

SELECT ?store ?name
WHERE {
    ?store a ex:Store ;
           ex:name ?name .
}
```

这展示了定义参与查询的一种方式。实际项目还需要明确引擎支持的语言范围，并验证公理变化怎样影响查询结果。

### 用 SHACL 检查数据

如果希望每个显式声明的便利店实例恰好有一个字符串名称，可以写一个 shape。

```turtle
@prefix ex: <https://example.org/business/> .
@prefix sh: <http://www.w3.org/ns/shacl#> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

ex:ConvenienceStoreShape a sh:NodeShape ;
    sh:targetClass ex:ConvenienceStore ;
    sh:property [
        sh:path ex:name ;
        sh:minCount 1 ;
        sh:maxCount 1 ;
        sh:datatype xsd:string
    ] .
```

校验器据此检查提交的数据图，并生成符合或违反约束的报告。业务来源是否完整、指标公式是否得到业务认可，还需要另外核验。[W3C SHACL 规范](https://www.w3.org/TR/shacl/)

## 如何在 Agent 项目中使用本体

可以把接入过程理解成五个步骤，每一步都对应一个能够检查的产物。

### 第一步，从一个具体问题建立业务模型

先选一个范围明确的问题，例如“查询某区域某个月的门店销售，并展示名单”。

围绕这个问题整理对象、关系、术语和身份。门店用什么完整键标识？交易关联哪种客户记录？地区属于门店所在地还是经销商所在地？销售月份采用什么业务日期？

产物可以先是一份简洁的概念表和关系表，由业务人员与开发者共同确认。接着将需要机器处理的部分表达成结构化定义或标准本体资源。

Nail 的实践让我特别重视身份。不同来源中的同名记录、相近地址和匹配候选，各自需要保存依据。来源编号中的前导零、空值和上下文，也需要进入身份约定。

### 第二步，把概念映射到真实数据

业务定义需要对应到具体来源。

例如，“门店”可以由一张门店表提供，“经销商向门店供货”可以由交易记录提供，“名单门店关联 POI”则来自经过核验的匹配结果。每种映射需要说明主键、关系方向、基数、版本和可用范围。

使用标准技术时，R2RML 可以描述关系数据如何映射成 RDF。Ontop 是一种虚拟知识图谱系统，它依据映射和支持的本体语义，把 SPARQL 转换为来源数据库执行的 SQL，数据可以继续保留在关系库中。[R2RML 规范](https://www.w3.org/TR/r2rml/)、[Ontop 官方介绍](https://ontop-vkg.org/guide/)

项目也可以先用结构化目录描述实体、关系和指标，由已有查询工具读取。采用这种方式时，需要明确语义解释与规则计算由哪些程序实现，逐项验证所支持的能力。

### 第三步，给 Agent 提供发现和查询能力

模型需要知道有哪些概念、哪些指标能够查询，以及工具接受什么参数。

一种接入方式是提供概念发现、定义读取和结构化查询工具。Agent 根据问题读取相关定义，形成查询请求。服务端再检查对象、字段、路径、参数和当前用户的权限。

```text
用户用业务语言提问
        ↓
Agent 发现概念并读取相关定义
        ↓
Agent 提交结构化查询请求
        ↓
服务端检查权限、范围和执行能力
        ↓
查询引擎或既有业务工具执行
        ↓
返回结果、口径与来源依据
        ↓
Agent 组织回答并引用图表或文件
```

上下文可以按问题逐步加载。比如用户查询覆盖率时，先提供门店、关联关系、覆盖率定义及相关工具。模型得到的定义和工具实际采用的定义，需要能对应到同一版本。

### 第四步，让指标和业务规则有明确的执行点

在本体周围建设业务语义层时，还需要定义指标的事实集、粒度、期间、单位、公式和缺失值处理，并将它们绑定到受审查询或确定性计算。

以覆盖率为例，假设市场范围有 100 家符合条件的门店，其中 20 家存在经确认的品牌关联，按这一定义覆盖率是 20%。如果先通过关联筛选出 20 家，再用它们作分母，结果就会变成 100%。

因此，分子和分母要共享规定的授权、期间与市场范围，同时分别保留各自筛选含义。关系连接产生多行时，还要检查重复计数。

Nail 的实验也记录了“有销”与净额的区别。某家店可能发生销售和退货，净额为零或负数，期间内仍有销售事实。这样的判断需要明确规则和输入条件。

权限同样由服务端和数据访问层执行。本体可以描述概念及其访问要求，实际请求仍需要根据当前身份逐次授权。

### 第五步，验证结果并保持交付一致

接入后，可以沿三个层次检查。

- **定义检查**，资源能否解析，类、关系和映射是否完整，约束正反例是否符合预期。
- **查询检查**，用固定样本和业务认可的报表核对身份、去重、金额、期间、单位与空值。
- **完整任务检查**，使用真实 Agent 问题，核对工具选择、最终回答、图表、地图、保存与导出。

一次查询的结果最好携带来源和定义版本。文字、图表与导出引用同一次保存的结果，用户才能核对它们之间的对应关系。

Nail 的探索中就出现过局部计算成功、完整交付受阻的情况，包括数值格式适配、正文校验误拒和组合查询超时。这些经历说明，完整任务验收需要覆盖从提问到最终产物的过程。

## 什么时候值得引入本体

当多个工具和数据源反复使用相同业务概念，身份关联复杂，指标口径需要共享，或者类型和关系推导具有明确价值时，本体能提供值得验证的组织方式。

可以先观察几个具体信号。团队是否反复解释同一个词？不同工具是否对同一个对象采用不同身份？一个指标是否维护着多套公式？新增查询是否需要反复手写相同关系？这些问题可以帮助确定建模范围。

引入标准本体与查询引擎后，需要持续维护语义资源、来源映射、执行绑定及其版本，并承担相应的查询性能和运行维护工作。可以先完成一个能对账的业务问题，再逐步扩大范围。

Nail 曾从自定义语义原型走向 Ontop 与 PostgreSQL 等标准组件，形成资源、运行时和隔离验证记录。归档中的完整模型任务仍有失败和待验收项。后来主线采用 Pi、Skill、只读 SQL 和地图工具继续发展，本体实现留存在独立分支。对具体项目而言，应用深度仍需结合业务收益和实际维护成本判断。

## 从哪里开始

初次在 Agent 项目里使用本体，可以先完成一项最小实践。

选一个真实问题，定义少量核心对象和关系，明确它们的身份与数据来源。再定义一项可对账的指标，通过工具完成查询，让回答和导出引用同一份结果。

有了这条可验证的执行过程，再逐步加入标准表达、图约束和确有需要的推理能力。本体的价值也可以在这个过程中被具体检查，概念是否更一致，查询是否更准确，规则是否更容易复用，以及结果是否更容易解释。
