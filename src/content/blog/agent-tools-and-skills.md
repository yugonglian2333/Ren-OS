“周六上午和下午，哪一场报名的人多？我得决定把大教室留给谁。”

能替你查报名表、算出结果再回答的助手，就是这里说的 **Agent**。要让它干好这件事，需要给它两样东西。**工具**是它可以调用的程序，比如查某天各场次的报名人数。**Skill** 是一份遇到这类问题时可以翻看的工作说明，比如用户问“人多不多”时该数人，问“收了几单”时该数报名单。

这点区别会改变教室分给谁。下面是虚构的五张有效报名单，一张可以报好几个人。

| 场次 | 每张单报了几人 | 单数 | 报名人数 |
| --- | --- | ---: | ---: |
| 上午 | 1、1、1 | 3 | 3 |
| 下午 | 2、2 | 2 | 4 |

只数表里有几行，上午赢。把每张单的人数加起来，下午赢。两种算法都能顺利跑完。做这个助手，麻烦的地方在于让它知道用户问的是哪一个数。

## 工具怎么设计，才能让助手查对数？

我会先给它一个工具，叫 `summarize_bookings`。工具说明写成一句人能读懂的话：“按场次统计指定日期的有效报名。可以数报名人数，也可以数报名单数。一张报名单可包含多人。”最后那句很要紧。工具名里有“报名”，读不出它的一行数据代表一个人还是一张单。[Anthropic 的工具设计实践](https://www.anthropic.com/research/writing-tools-for-agents)

用户问的是教室要坐多少人。在这个例子里，助手交给工具的参数是 `{"day":"2030-06-08","measure":"people"}`。工具应当把单位和数字一起交回来。

```json
{
  "day": "2030-06-08",
  "measure": "people",
  "unit": "人",
  "rows": [
    {"session": "上午", "value": 3},
    {"session": "下午", "value": 4}
  ]
}
```

有了这份结果，助手就可以答：“下午报名的人更多，4 人，比上午多 1 人。大教室留给下午。”如果用户接着说“画出来给我看”，画图工具可以直接使用这两行和单位。要是为了画图又查一遍，中途刚好多了一笔报名，图上就可能有 5 人，上一句话里还写着 4 人。

这里用到的 **参数 Schema**，就是程序能检查的一张填表说明。下面这段约定了日期和统计方式都要填，后者只有两种填法。应用还要检查日期是否真实存在，比如 6 月 31 日应当退回。[JSON Schema 的对象与必填字段](https://json-schema.org/understanding-json-schema/reference/object)

```json
{
  "type": "object",
  "properties": {
    "day": {"type": "string", "description": "活动日期，格式为 YYYY-MM-DD"},
    "measure": {"type": "string", "enum": ["people", "bookings"]}
  },
  "required": ["day", "measure"],
  "additionalProperties": false
}
```

为什么把 `measure` 设为必填？因为这五张单已经给了一个反例。如果默认数单，忘填一次，答案就从下午变成了上午。设为必填能抓住漏填。至于助手明明该选人数却选了合法值 `bookings`，输入检查照样会通过。这就轮到 Skill 发挥作用了。

## Skill 写什么，助手才用得上？

如果让我把这件事交给一个新同事，我会提醒他：“一单能报多人。分教室就看人数，核对收了几张单才看单数。”这两句话值得写进 Skill。查哪张表、怎么加总，交给工具实现就行。以后报名表换了存储方式，只要“报名人数”的含义没变，这份工作说明仍然能用。

按 Agent Skills 的约定，可以把这份说明放在 `booking-summary/SKILL.md`。文件开头的 `description` 用来说明它在什么情况下有用。支持按需加载的助手先看到名称和简介，遇到报名统计任务时才读取正文。这样，回答其他问题时也不用带上工坊的整份说明。[Agent Skills 格式规范](https://agentskills.io/specification)

```markdown
---
name: booking-summary
description: 比较活动各场次的报名情况，适用于安排教室、核对报名人数或报名单数。
---

安排教室或问多少人报名时，调用 summarize_bookings，measure 选 people。
问收了几张报名单时，选 bookings。已经说过的日期继续沿用。
如果只问“哪场更热门”，而人数和单数会影响决定，先问一句“你想比人数还是单数？”
答复时带上单位。如果还要画图，沿用刚查到的数据。
```

“哪场更热门”值得追问，“哪场报名的人多”已经说清楚了。给两句问法都安排一轮确认，只会让已经讲明白的用户重复一遍。至于只问一句数字要不要画图，也可以留给当次需求决定。把每个可用工具都写成必经步骤，简单查询就会平白多出一张没人要的图。

## 查不到时，工具怎样告诉助手？

把用户的问题换成“下午实际来了几个人”。报名表能证明 4 人报名，查到场人数还需要签到记录。即使助手把 `measure` 换成 `attendance`，这个统计工具也算不出答案。应用可以将参数校验失败转成下面这条错误，交回给助手。

```json
{"error": "unsupported_measure", "supported": ["people", "bookings"], "detail": "报名数据只记录报名人数和单数。实际到场人数需查签到记录。"}
```

这时就有了一句诚实又有用的答复：“下午报了 4 人。手上只有报名表，实际来了几人得看签到记录。”如果查报名的服务暂时连不上，则连“报了 4 人”都不能从这次调用中得出。工具应当报告查询失败。只有在查询成功、确实覆盖了所问场次且有效报名为零时，助手才有依据说“没人报名”。

验收这个 Agent，可以先用纸上这五张单问它三遍。问“哪场要大教室”，应看到按人数查询，答案是下午。问“哪场收的单多”，应看到按单数查询，答案变成上午。问“下午实际来了几人”，应听到它说明还差签到记录。只要一次答错，再看它传给工具的参数和工具返回的单位，就知道该改工作说明、改计算，还是改最后那句话。
