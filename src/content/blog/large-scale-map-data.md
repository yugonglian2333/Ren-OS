把地图拖到另一个城市，过一会儿，新区域里出现了点和数字。这些点是从哪来的？为什么缩小地图后，许多点又变成了几个大数字？

大规模地图通常不会在打开页面时把所有坐标一次塞进浏览器。页面先把**当前能看到的地图范围**发给服务器，服务器只查这片区域，并按当前缩放级别决定返回门店点还是统计格子。这样做省下的请求数据能不能画对，还取决于三个细节：范围有没有查全、格子有没有数对、页面最后展示的是不是最新一批结果。

## 先算清视窗里的数据

想象一张地图只显示横坐标 0 到 4、纵坐标 0 到 2。数字只是虚构的平面位置，读者可以按格子手算，不涉及真实地址。图上有下面 4 个点：

| 点 | 坐标 |
| --- | --- |
| A | (0.5, 0.5) |
| B | (1.5, 0.5) |
| C | (3.5, 1.5) |
| D | (4.5, 0.5) |

当前地图范围是矩形 `[0, 4] × [0, 2]`，所以 D 在屏幕以外。服务器只该把 A、B、C 返回。若回答“框内有多少门店”，答案应当是 **3**。

把地图放大或缩小，会改变当前可见矩形。拖动和缩放没有改变用户选的业务范围，例如“某个已授权的区域”。这两件事要分清：视窗决定**本次取哪些数据来画**，业务范围决定**用户有权统计哪些数据**。如果拖地图就把总数从全部授权门店变成“当前屏幕 3 家”，一个纯粹的镜头动作就悄悄改了统计口径。

## 把点变成格子，先约定怎么算

地图缩小到全国时，四个点全挤在屏幕一角，逐个画出来既难读也费资源。可以先将地图切成同样大小的方格。每个方格返回“里面有几个点”，于是 A、B 在同一格中时显示为 **2**，C 显示为 **1**。

| 格子 | 区间 | 覆盖门店 |
| --- | --- | --- |
| 左下格 | x ∈ [0, 2)，y ∈ [0, 1) | A、B |
| 右上格 | x ∈ [2, 4]，y ∈ [1, 2] | C |

数格子有个边界规则：格子通常取左下边界、排除右上边界，最后一行／列可单独封住整体边界。否则在共享边界上的点可能被数两遍，或者漏掉。要求“当前视窗内的精确点数”时，还要和原始视窗相交后再判断点坐标，不能拿“相交方格的完整计数”冒充视窗内的精确点数。

地图方格的级别也会随缩放变化。放大后用较小的格子，让用户看见分布细节；缩小后用较大的格子，避免屏幕上出现成千上万个图标。**一个格子汇总多少点，是显示口径。业务统计的范围仍按用户选择和授权规则计算。**地图数据接口应该把总数、格子计数和点位数量分别命名，避免客户端拿着一个含糊的 `count`，时而表示格子数、时而表示完整门店数。

## 地图上的“经纬度”不能拿来当屏幕距离

数据库里的坐标常使用经纬度。经度、纬度是角度，向东一度对应的地面距离会随纬度变化。若在经纬度上把固定的 0.01 度当成“每格 1 公里”，不同地方的格子就不是同一个物理大小。

因此服务端选了方格坐标系后，要先确认点位和视窗是否使用同一坐标参考，再做范围比较与计数。**给坐标贴上不同 SRID 名称，不会把点移到另一个坐标系。**若确实要在不同参考系间比较，需要做坐标转换；PostGIS 的 `ST_Transform` 会转换坐标值，`ST_SetSRID` 则只改变参考系标记。[PostGIS 的坐标转换说明](https://postgis.net/docs/ST_Transform.html)

用视窗矩形查询点位时，`ST_Intersects` 可以检查点和矩形是否有共同区域，并可利用可用的空间索引做包围盒比较。大量点位下，索引能帮助跳过远离视窗的区域，数据库仍要检查候选结果是否真的相交。[PostGIS 的空间相交查询](https://postgis.net/docs/ST_Intersects.html)

这也是为什么“返回上限”要和查询完整性一起设计。接口若只返回视窗内的前 500 个点，却仍说是完整结果，地图上会显得局部数据稀少。可以在低倍返回完整格子计数，高倍返回完整的可见点位，并检查上限是否截断。若视窗数据可能超过上限，应继续分片、聚合，或明确告诉页面结果不完整，不能把前 500 个伪装成整片地图。

## 快速拖动时，旧结果为什么会盖住新结果？

拖动地图会连续触发请求。比如 R1 查的是“框 A”，R2 随后查“框 B”。如果 R2 比 R1 先返回，页面先显示了框 B；几毫秒后 R1 才完成，若无条件把结果写进状态，地图就退回框 A。虽然服务端查得都没错，读者看到的却是旧位置的数据。

通常会同时处理两件事：

1. 用 `AbortController` 取消已经不需要的请求，少浪费网络、CPU 和数据库资源。浏览器 Fetch API 支持通过 `AbortSignal` 接收取消信号。[MDN 的 AbortController 说明](https://developer.mozilla.org/en-US/docs/Web/API/AbortController)
2. 每次请求带一个递增编号。结果回来时，只有编号仍等于“最新请求编号”的那一份可以更新地图。取消是节省资源，编号检查是保护页面状态，两者作用不同。

取消信号也可能晚到，或者请求在服务器端已经开始计算。客户端仍要做返回时检查。变更筛选条件时同样应该取消和替换请求，因为旧筛选的点位如果先回到新地图上，短暂显示也会误导用户。

## 缓存应当复用同一个问题的答案

把响应缓存起来能避免用户回到刚看过的区域时再查一次，但缓存键要描述完整问题。比如业务范围、权限身份、数据版本、筛选条件、缩放等级、视窗范围和聚合算法版本都会改变答案。漏掉筛选条件，“只看餐饮”的结果就可能被“所有门店”的请求复用；漏掉坐标或格子算法版本，新计算方式也可能误用旧格子。

这里会有一个性能和正确性之间的取舍：缓存范围小，结果更贴近用户看到的窗口，却容易因轻微平移而一次也命不中。缓存较大的格网或切片更容易复用，但要把格网版本、边界规则和计算口径一起固定。**只要缓存命中的含义不变，返回数据才算复用成功。**

判断地图数据有没有算对，我会拿上面的四个点分别核视窗结果、格子计数，再模拟 R1、R2 逆序返回。最后问自己：用户只拖动了镜头时，屏幕上的图变了，业务总数和授权范围有没有跟着被偷偷改变？
